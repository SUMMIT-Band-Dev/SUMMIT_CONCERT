# work02 — Nest.js 백엔드 추가

> 이 문서는 **Nest.js 백엔드/인증 작업(work02)을 시작할 때만** 참조합니다.

## 상태

예정. work01(리팩토링) 이후 착수.

## 목적

SUMMIT을 순수 프론트엔드 프로젝트에서 "프론트 메인 + 필요에 의한 백엔드 확장" 구조로 넓힘. work03의 어드민 페이지(데이터 CRUD)가 이 백엔드 위에서 동작하는 것이 최종 목표.

**포지셔닝 원칙**: 서류/자소서에서는 "프론트엔드가 메인, 백엔드는 필요에 의한 확장"으로 명확히 함 — 백엔드를 SUMMIT의 메인 서사로 쓰지 않음.

## Phase 구분 (필수)

이전에 "새 프로젝트 없이 SUMMIT 내 API 1개만 최소 구현"으로 스코프를 타협했던 적이 있음. 완성형 백엔드로 욕심을 낼 수 있지만, 우선순위 충돌 시 반드시 아래 기준을 따름.

### Phase 1 — 최소 API 1개 (여유 있으면 9~10월 중 시도)

- 범위: 공연별 신청 현황 집계, 참여 통계 API 등 1개 (SQL JOIN/GROUP BY 학습과 묶어서 처리)
- **중단 조건**: work01의 진행을 조금이라도 늦추면 즉시 중단하고 Phase 2로 이월. 판단을 미루지 말 것
- Phase 1이 9-10월 안에 끝나지 않으면 자동으로 Phase 2로 통합

### Phase 2 — 완성형 백엔드 + 인증 로직 (work02 본작업)

- 범위: NestJS 백엔드 전체 구현 + 로그인/인증 로직
- **인증 로직은 본인이 직접 구현** — SWYP 프로젝트에서는 백엔드 팀원이 인증을 담당했던 것과 구분되는 지점. 포트폴리오 서사에서 "SUMMIT은 인증까지 직접 설계·구현"으로 명시 가능
- 인증/세션 관련 작업은 배포 전 충분한 테스트 없이는 사고 위험이 큰 영역 — `develop` 브랜치에서 `feature/auth-*` 단위로 격리 작업 후 검증 후 머지
- work03(어드민 페이지)이 이 백엔드의 첫 실사용처가 됨 — 어드민 요구사항(로그인 + 텍스트/이미지 CRUD)을 초과하는 API를 미리 만들지 않음. 과설계 방지

## 레포/브랜치 구조

- **레포 분리 안 함** — 모노레포 유지 (`apps/web`, `apps/api`)
  - 이유: 1인 풀스택 개발 + 프론트/백 결합도가 높은 프로젝트 특성상, 레포 분리로 얻는 "권한 분리" 이점이 없음. 타입 공유, PR 단위 완결성, CI/CD 단순화 등 모노레포 이점이 훨씬 큼
  - 2027년 팀원 합류로 역할이 프론트/백으로 명확히 나뉘면 그때 재검토
- **브랜치는 기능 단위로** (`feature/login`처럼 프론트+백 동시 포함), 프론트/백 기준으로 나누지 않음
- 폴더 세팅(`apps/api` 스캐폴딩)은 지금 미리 하지 않고, Phase 착수 시점에 최신 Nest.js 버전으로 진행 — 버전 드리프트 방지
- 기술 스택 상세는 착수 시점에 `.claude/rules/backend/`에 별도 정리 (현재 비어있음)

## 팀원 합류 대비

- `.vscode/settings.json`은 팀 공유용으로 커밋 (포맷터/린터 설정 통일). 개인 취향(테마 등)은 VSCode User Settings로 분리
- `.vscode/extensions.json` 추가해 권장 익스텐션 목록 관리 고려
- 2027년까지 백엔드 담당 팀원이 합류할 가능성을 염두에 두고 구조 설계 — 지금은 1인이 프론트/백 다 맡으므로 레포·문서를 과도하게 나누지 않되, 온보딩 문서(`CONTRIBUTING.md`류)는 팀원 합류 전에 정리
