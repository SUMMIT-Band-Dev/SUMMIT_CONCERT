# work02 — Nest.js 백엔드 추가

> 이 문서는 **Nest.js 백엔드/인증 작업(work02)을 시작할 때만** 참조합니다.

## 상태

**착수 (2026-09-19)**. work01(리팩토링) 완료(추석 전 목표)를 기다리지 않고, 착수 조건인 DB 스키마 정리 + RLS 활성화가 이번에 끝나 즉시 시작함. 이전에는 콘텐츠 마이그레이션(work03-A) 완료 후 착수하는 순서였으나, 백엔드를 1학기 기존 데이터 기반으로 먼저 확실하게 구축하는 쪽으로 변경. 콘텐츠 마이그레이션은 더 이상 백엔드 착수/완성의 선행 조건이 아니며, 임원진 데이터 도착 일정에 따라 병렬/독립 트랙으로 진행됨 (`.claude/rules/work-03-update.md` 참조).

## 착수 배경 (2026-09-19)

work02 착수 직전 아래 두 작업을 프로덕션 Supabase에 완료함 (상세 배경/문제/변경/검증은 `REFACTOR_NOTES.md` §8 참조):

1. **DB 스키마 마이그레이션 (FK 전환)**: `Setlist.team`(문자열) 매칭 방식을 `Setlist.teamId`(FK → `Line Up.id`) 구조로 전환. `Line Up`에 `performanceOrder` 컬럼 추가. 관리자 페이지에서 팀명 수정 기능을 넣을 계획인데, 문자열 매칭 구조로는 팀명 수정 시 연결이 깨지는 문제가 있어 이번에 정규화함
2. **RLS(Row Level Security) 활성화**: `Setlist`, `Line Up` 두 테이블 모두 RLS disabled 상태 → anon key로 쓰기까지 가능했던 취약점을 SELECT 전용 정책 추가로 해소. anon key는 이제 읽기만 가능

이 두 변경 덕분에 Nest.js가 처음부터 정규화된 스키마와 보안 정책 위에서 시작할 수 있는 상태가 됨.

## 목적

SUMMIT을 순수 프론트엔드 프로젝트에서 "프론트 메인 + 필요에 의한 백엔드 확장" 구조로 넓힘. 단순 CRUD 이관이 아니라, 로그인(JWT) + 팀/곡 관리자 기능을 갖춘 진짜 풀스택 구조로 전환하는 것이 목표. work03의 어드민 페이지(데이터 CRUD)가 이 백엔드 위에서 동작하는 것이 최종 목표.

**포지셔닝 원칙**: 서류/자소서에서는 "프론트엔드가 메인, 백엔드는 필요에 의한 확장"으로 명확히 함 — 백엔드를 SUMMIT의 메인 서사로 쓰지 않음.

## 연결 방식

- Nest.js는 Supabase PostgREST를 거치지 않고 **Postgres DB에 직접 연결** (Prisma 또는 TypeORM)
- DB 자체(Postgres 인스턴스)는 Supabase가 그대로 호스팅, 연결 방식만 변경됨 — 프론트엔드(Next.js)는 기존과 동일하게 Supabase 클라이언트로 읽기 전용 접근 유지

## "완성"의 정의 (2026-09-19 확정)

백엔드 완성 조건을 두 단계로 분리해서 기록한다. 이 둘을 뭉뚱그리지 않는 것이 중요 — 1차 완료만으로 11월 서류 시점의 "구축 완료" 서사를 쓸 수 있어야 함.

- **1차 완료 조건 (필수, 11월 서류 시점 전 목표)**: **1학기 기존 데이터**를 기준으로 로그인 + 팀/곡 CRUD가 정상 동작. 2학기 데이터 도착 여부와 무관하게 이 시점에 "백엔드 구축 완료"로 간주
- **2차 완료 조건 (별도, 데이터 도착 시점에 진행)**: 2학기 콘텐츠가 도착하면 **동일 스키마**에 데이터만 채워 넣음 (2학기 공연 구성이 1학기와 동일하여 스키마 변경 불필요함을 확인함). 이는 work03-A(콘텐츠 마이그레이션) 작업이며 백엔드 완성과는 별개 트랙

## 관리자 페이지 최종 기능 스코프 (2026-09-19 확정)

- **로그인**: JWT 기반 관리자 인증. 기존 서비스 로그인과 무관 — 관리자 전용 접근 권한
- **팀(Line Up) CRUD**: 팀명 + 공연순서(`performanceOrder`) + 공연일자(`day`) 세트 업로드, 재정렬 기능, 카드뉴스 사진 업로드
- **곡(Setlist) CRUD**: 팀 선택 시 해당 팀 곡만 조회하는 패널 구조, 곡 제목/가수/유튜브 URL 수정
- **앨범 커버 자동검색**: 곡 제목+가수 입력 시 자동으로 앨범 커버를 찾아 채움 (iTunes Search API 예정)
- **유튜브 연결 관리**: 기존 실시간 폴백 로직(top-video 검색+스코어링, `src/app/api/youtube/`; **work02-7b에서 프론트 라우트 삭제, 이후 영상 링크가 없는 곡은 YouTube 검색 결과 링크로 연결**)을 배치 처리로 확장, `youtube_url`이 NULL인 곡들을 일괄 리뷰(추천 영상 미리보기 + 승인/직접수정)하는 관리자 UI

work03(어드민 페이지)이 이 백엔드의 첫 실사용처이며, 위 스코프를 초과하는 API는 지금 단계에서 미리 만들지 않는다 — 과설계 방지.

## 빌드 순서 (확정)

1. NestJS 프로젝트 세팅 + Postgres 직접 연결 (Prisma `db pull`로 기존 스키마 가져오기)
2. Auth 모듈 (JWT 로그인)
3. Team CRUD (세트 업로드 + 재정렬)
4. Song CRUD + 앨범 커버 자동검색 연동
5. 카드뉴스 사진 업로드 (Supabase Storage 연동)
6. 유튜브 배치검색 + 리뷰용 엔드포인트 (기존 `/api/youtube/top-video` 로직 이관+확장 — 6단계에서 이관 완료, 프론트 라우트는 work02-7b에서 삭제)
7. 관리자 프론트 UI (팀 목록 패널 + 선택 팀 곡 편집 패널)

- 인증 로직은 본인이 직접 구현 — SWYP 프로젝트에서는 백엔드 팀원이 인증을 담당했던 것과 구분되는 지점. 포트폴리오 서사에서 "SUMMIT은 인증까지 직접 설계·구현"으로 명시 가능
- 인증/세션 관련 작업은 배포 전 충분한 테스트 없이는 사고 위험이 큰 영역 — `develop` 브랜치에서 `feature/auth-*` 단위로 격리 작업 후 검증 후 머지
- **스코프 경계 재확인**: 아카이빙 페이지 등 신규 기능 아이디어는 완전히 별개의 백로그 항목이며 이 작업에 포함하지 않음 (착수 여부 자체도 미결정)

## 레포/브랜치 구조

- **레포 분리 안 함** — 모노레포 유지 (`apps/web`, `apps/api`)
  - 이유: 1인 풀스택 개발 + 프론트/백 결합도가 높은 프로젝트 특성상, 레포 분리로 얻는 "권한 분리" 이점이 없음. 타입 공유, PR 단위 완결성, CI/CD 단순화 등 모노레포 이점이 훨씬 큼
  - 2027년 팀원 합류로 역할이 프론트/백으로 명확히 나뉘면 그때 재검토
- **브랜치는 기능 단위로** (`feature/login`처럼 프론트+백 동시 포함), 프론트/백 기준으로 나누지 않음
- 폴더 세팅(`apps/api` 스캐폴딩)은 착수 시점에 최신 Nest.js 버전으로 진행 — 버전 드리프트 방지
- 기술 스택 상세는 착수 시점에 `.claude/rules/backend/`에 별도 정리 (현재 비어있음)
